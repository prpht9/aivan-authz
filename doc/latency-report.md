# Latency under load

Measured 2026-11-13. This is the evidence for acceptance 9 and the numbers in
spec §8.2.

## What was measured

`test/load/verify.js` drives the phase file's mixed traffic against
`/__aivan/verify`:

| Share | Case | Expected |
|---|---|---|
| 70% | accept — a live nonce from a pre-filled pool, a real P-256 signature | `200` |
| 20% | replay — a nonce that VU already spent | `401` |
| 10% | no proof — no device and no cookie | `401` |

Nonces are generated by `test/load/seed` into the database and read from a file,
so the accept case costs the verify statement alone. Issuing a nonce per request
would put the nonce endpoint in front of every sample.

Two runs are reported because the phase names two claims:

- **Handler** — the script posts the forwarded headers straight at the gate's
  handler. This is the "p99 decision latency under 5 ms at the gate's own
  handler" claim.
- **End to end** — the script requests a gated application path and Traefik makes
  the auth call. This is the "p99 end-to-end through Traefik under 10 ms" claim.

The end-to-end run used a local Traefik v3.7.13 with the deployed middleware
configuration (same `authRequestHeaders`, `forwardBody`, `maxBodySize: 2097152`,
`preserveRequestMethod`, `preserveLocationHeader`), an application that reads the
body and echoes its `Content-Length`, and a self-signed certificate. It ran on
the same machine as the gate and a local PostgreSQL 18, so the number includes
one proxy hop, one TLS handshake per connection, and the gate's own work — but
not the cluster's CNI hop or the cluster database.

## Result: 200 rps sustained, 3 minutes

Both runs held exactly 200.0 requests a second (`constant-arrival-rate`,
`rate: 200`). The ramping profile in the phase file is also implemented
(`AIVAN_PROFILE=ramp`) and was run for completeness; it spends most of its life
below 200, so its summary mixes the ramp into the percentiles and is not the
sustained figure.

### At the gate's handler

```console
$ k6 run -e AIVAN_PROFILE=steady200 -e AIVAN_VIA=handler \
    -e AIVAN_TARGET=http://127.0.0.1:18080 test/load/verify.js

aivan_accepted........: 25181   139.9/s
aivan_replayed........:  7177    39.9/s
aivan_refused_no_proof:  3643    20.2/s
aivan_wrong_status....:     0
aivan_unavailable.....:     0
aivan_verify_ms.......: avg=1.45ms p(50)=1.48ms p(95)=1.67ms p(99)=1.99ms max=19.87ms
http_reqs.............: 36000   200.0/s
```

| Metric | p50 | p95 | p99 | max |
|---|---|---|---|---|
| decision at the handler (`aivan_verify_ms`) | 1.48 ms | 1.67 ms | **1.99 ms** | 19.87 ms |
| whole HTTP request | 1.42 ms | 1.64 ms | 1.94 ms | 19.87 ms |

### End to end through Traefik

```console
$ k6 run -e AIVAN_PROFILE=steady200 -e AIVAN_VIA=traefik \
    -e AIVAN_TARGET=https://aivan-hud.home.arpa:18443 \
    -e AIVAN_RESOLVE=aivan-hud.home.arpa:127.0.0.1 test/load/verify.js

aivan_accepted........: 25161   139.8/s
aivan_replayed........:  7224    40.1/s
aivan_refused_no_proof:  3615    20.1/s
aivan_wrong_status....:     0
aivan_unavailable.....:     0
aivan_verify_ms.......: avg=3.42ms p(50)=3.07ms p(95)=5.85ms p(99)=7.66ms max=41.29ms
http_reqs.............: 36000   200.0/s
```

| Metric | p50 | p95 | p99 | max |
|---|---|---|---|---|
| request through the proxy (`http_req_duration`) | 2.88 ms | 5.66 ms | **7.46 ms** | 41.29 ms |
| the same request's decision time (`aivan_verify_ms`) | 3.07 ms | 5.85 ms | 7.66 ms | 41.29 ms |

Both claims hold: 1.99 ms at the handler against a 5 ms budget, and 7.46 ms end
to end against a 10 ms budget.

### The other two conditions

- **No 503s.** `aivan_unavailable` counted zero in both runs, and
  `aivan_wrong_status` counted zero, so every accept was a 200 and every refusal
  was the expected 401. The gate logs no `database_error` decision in either run.
- **No connection-pool waits.** The gate logs its pool statistics at shutdown:

```console
$ kubectl -n hermes-agent logs deploy/aivan-authz | tail -1
{"msg":"stopped","acquires":32413,"acquire_avg_us":3,"connections_created":16,
 "canceled_acquires":0,"max_conns":16,"total_conns":16}
```

`acquire_avg_us` is the mean time a request spent getting a connection: 3 µs,
which is the pointer swap of a warm pool. `canceled_acquires` is zero, which is
the count that would matter if requests were giving up while queued.

## Settings, and what changed to reach them

| Setting | Value | Why |
|---|---|---|
| `http_reqs` arrival | 200/s constant | the phase's sustained figure |
| VUs | 100 pre-allocated, 100 max | each iteration is ~3 ms of work plus one signature; 3–4 are busy at a time, the rest is headroom for a slow second |
| Pool `MaxConns` | 16 | one statement of ~300 µs per request is far below what 16 connections serve |
| Pool `MinConns` | 2 | pgxpool's floor |
| Warm connections at startup | all 16 | see below |
| Prepared statements | all nine, prepared at connection open | no request pays a Parse |
| Rows per group in the verify statement | one row | `array_agg` over the role list of one user, which is a handful of rows and never spills |

Two changes came out of the first runs:

1. **The pool was cold at the first request.** With `MaxConns: 16` and no warm
   connections, the first second of a run paid a dial per connection and showed
   as connection-pool waits. `store.Warm` now acquires the whole pool before the
   listener opens, so a slow database is a start failure rather than a slow
   first request. After the change, `connections_created` equals `MaxConns` and
   every one of them was created at startup.
2. **The script's `http_req_timeout` option was not a k6 option.** It was
   silently ignored; the per-request timeout is now passed to `http.get`.

The phase file's order of investigation — pool size versus VUs, whether the
prepared statement is reused, whether `array_agg` spills — was followed: pool
size was the one that mattered, and it mattered only for the first second.

## Reproducing

```console
# 1. A scratch database with the fixture and the migrations.
createdb aivan_load
psql -d aivan_load -f test/fixtures/hud_min.sql
AIVAN_DB_URL=postgres://.../aivan_load go run ./cmd/authz migrate

# 2. One person and one device key, plus 100k nonces.
psql -d aivan_load -c "insert into public.users (id, username, active) values (10,'loaduser',true)"
eval "$(go run ./test/load/seed -dsn "$DSN" -user 10 -count 100000 -kind tablet -jwk-env)"

# 3. The gate.
AIVAN_DB_URL=$DSN AIVAN_HOSTS=aivan-hud.home.arpa AIVAN_POLICY=./policy.yaml \
  AIVAN_LISTEN=127.0.0.1:18080 ./authz serve

# 4. Handler-only.
k6 run -e AIVAN_PROFILE=steady200 -e AIVAN_VIA=handler \
   -e AIVAN_TARGET=http://127.0.0.1:18080 -e AIVAN_LOAD_DEVICE="$AIVAN_LOAD_DEVICE" \
   -e AIVAN_LOAD_JWK="$AIVAN_LOAD_JWK" test/load/verify.js
```

`test/load/seed` prints `AIVAN_LOAD_DEVICE` and `AIVAN_LOAD_JWK` as shell
assignments when given `-jwk-env`. It writes a device row and nonce rows with
whatever credential its `-dsn` names, so it runs as the migration role, never as
the gate's own role.

A nonce is single use. A second run against the same pool file would present
spent nonces and every accept would be a `nonce_unknown` 401; `-nonce` files are
consumed from the front, and `AIVAN_NONCE_OFFSET` skips what an earlier run used.
